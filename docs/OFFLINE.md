# Offline expenses and the sync log

Callable functions need a connection. Trips in the mountains often don't have one, so
**adding, editing and voiding expenses works offline** through a queue in Firestore:

1. The app writes each change as a document in `expenseOps/{opId}` with the Firestore SDK.
   Offline, the SDK keeps the write on the device (it survives app restarts) and sends it
   automatically when the connection comes back. No callable is involved.
2. The `processExpenseOp` Firestore trigger applies the change on the server, using the
   same code, validation and permissions as `createExpense` / `updateExpense` / `voidExpense`.
3. The op document is updated with the outcome. It is the user's **sync log**: which trip,
   what was changed, when it was made on the phone, and whether it was applied.

UPI payments are not part of this: paying needs a connection anyway (the UPI app needs one),
and payments must reach the server before the UPI app opens.

## The op document (what the app writes)

| Field | Value |
|---|---|
| doc id, `opId` | A new UUID per change. Both must be the same. |
| `uid` | The signed-in user's uid. |
| `tripId` | The trip the change belongs to. |
| `type` | `CREATE_EXPENSE`, `UPDATE_EXPENSE` or `VOID_EXPENSE`. |
| `expenseId` | For a create, a **new UUID generated by the app**: the expense gets this id, so it can be shown and edited before it syncs. For an edit or void, the expense's id. |
| `payload` | The same fields as the callable, without `tripId`, `expenseId` and `idempotencyKey`. Create: `title`, `amountMinor`, `participantUids`, `split?`, `paidByUid?`, `merchantName?`, `categoryId?`, `notes?`, `expenseDate?`, `receiptIds?`. Update: `expectedVersion` plus the changed fields. Void: `expectedVersion`, `reason`. |
| `clientCreatedAt` | When the user made the change (a Timestamp from the phone's clock). |
| `status` | `"PENDING"`. |
| `createdAt` | Optional: server timestamp. |

No other fields are allowed; an unknown field rejects the op.

## What the server adds

| Field | Meaning |
|---|---|
| `status` | `PENDING` (not synced yet), `DEFERRED` (an edit waiting for its expense's offline create), `APPLIED`, `REJECTED`, or `FAILED` (an unexpected error that persisted for 30 minutes; safe to redo). `PROCESSING` appears briefly. |
| `tripName` | The trip's name when the change was applied. |
| `result` | The callable's response, e.g. `{ expenseId, version, shares }`. |
| `error` | For `REJECTED` / `FAILED`: `{ code, reason, message }`, with the same `reason` codes as the callables. |
| `processedAt`, `attempts` | When it was last processed, and how many times. |

The trip's activity log (`listAuditLogs`) also marks these changes: `metadata.source` is
`OFFLINE_SYNC`, with `metadata.clientAt` (when it was made on the phone) and `metadata.opId`.

## Order and conflicts

* **Create, then edits, all offline.** Edits that reach the server before their create are
  `DEFERRED` and applied right after it, in the order the user made them.
* **Several offline edits of the same expense.** The app only saw one version, so every edit
  carries that same `expectedVersion`. That's fine: when every change since that version was
  the same user's own, the edit is applied.
* **Someone else changed the expense meanwhile.** The offline edit is `REJECTED` with
  `VERSION_CONFLICT`, and the other person's change is kept. The app should show this in the
  sync log and let the user redo the edit on the current version.
* **Not allowed.** Anything the callable would refuse (not a member, not the creator/payer/admin,
  confirmed expense, bad split) is `REJECTED` with the same `reason`.
* Expense dates default to `clientCreatedAt`, not to the time it synced.

## Security Rules to add (in FlutterFlow)

Security Rules are managed in FlutterFlow, so this repo doesn't deploy them. The queue needs
these rules; without the `create` rule, the app can't write ops at all.

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    function signedIn() { return request.auth != null; }
    function isMember(tripId) {
      let m = /databases/$(database)/documents/tripMemberships/$(tripId + "_" + request.auth.uid);
      return signedIn() && exists(m) && get(m).data.status == "ACTIVE";
    }

    // Offline queue: users create their own ops and read their own log. Only the server updates them.
    match /expenseOps/{opId} {
      allow create: if signedIn()
        && request.resource.data.uid == request.auth.uid
        && request.resource.data.opId == opId
        && request.resource.data.status == "PENDING"
        && request.resource.data.type in ["CREATE_EXPENSE", "UPDATE_EXPENSE", "VOID_EXPENSE"]
        && isMember(request.resource.data.tripId);
      allow read: if signedIn() && resource.data.uid == request.auth.uid;
      allow update, delete: if false;
    }

    // Read-only access for trip members, so screens can load from the offline cache.
    match /trips/{tripId} { allow read: if isMember(tripId); }
    match /tripMemberships/{id} { allow read: if signedIn() && (resource.data.uid == request.auth.uid || isMember(resource.data.tripId)); }
    match /expenses/{id} { allow read: if isMember(resource.data.tripId); }
    match /expenseSplits/{id} { allow read: if isMember(resource.data.tripId); }
    match /categories/{id} { allow read: if isMember(resource.data.tripId); }
    match /transactions/{id} { allow read: if isMember(resource.data.tripId); }
    match /settlements/{id} { allow read: if isMember(resource.data.tripId); }
  }
}
```

Merge these into your existing rules rather than replacing them; keep whatever FlutterFlow
generated for `users` and your own collections. No client writes are allowed to any backend
collection other than `expenseOps`. Queries on trip collections must filter on `tripId`
(for example `where tripId == X`) so the rules can check membership.

`processExpenseOp` also checks, as a second line, that the writer Firestore reports matches
`uid`, and every op is re-validated against membership and permissions when applied.

## Reading data offline

The Firestore SDK caches documents it has read, so screens that read Firestore directly
keep working offline with the last data seen. Screens that call functions (`listExpenses`,
`getTripSummary`, ...) don't. For offline use:

* Trip list: query `tripMemberships` where `uid == me` and `status == "ACTIVE"`, then `trips`.
* Expense list: query `expenses` where `tripId == X`, ordered by `expenseDate` desc.
* Pending changes: query `expenseOps` where `uid == me` and `tripId == X`; show items with
  status `PENDING` / `DEFERRED` as "Waiting to sync" on top of the list (offline, newly created
  expenses exist only here until they sync).
* Sync log screen: query `expenseOps` where `uid == me` (optionally `tripId == X`), ordered by
  `clientCreatedAt` desc. Online, `listSyncLog` returns the same list.

Balances (`getTripSummary`) are calculated on the server and need a connection; show the last
loaded summary with a "may be out of date" note when offline.

## Indexes

`firestore.indexes.json` includes the composite indexes the trigger and the queries above use.
Deploy them with `firebase deploy --only firestore:indexes` (merge with FlutterFlow's first).
